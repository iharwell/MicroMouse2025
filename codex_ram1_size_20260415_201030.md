## Summary

The main RAM1 story is:

1. RAM1 code is the dominant RAM1 consumer.
2. RAM1 variables are spread across several medium-sized always-live globals and mode singletons.
3. The large `mmlog` DMA queue is not part of the RAM1 problem; it lives in RAM2.

## Practical Conclusion

If the goal is to reduce RAM1:

- For RAM1 variables, the most obvious targets are mode singletons, generated `mmlog` header strings, math tables, and long-lived globals like `_hsp` and `gWallDistanceCalibration`.
- For total RAM1 usage, code size is the larger problem. The biggest code owners are `MissionController`, UKF/plant/math paths, calibration helpers, and utility/measurement-mode logic that is linked into the same firmware image.

## Explicit Non-Issue For This Note

The large `mmlog` DMA buffers are not part of RAM1:

- `g_primaryStorage`: 262,144 bytes
- `g_sidecarStorage`: 4,096 bytes

Those live in RAM2, not RAM1.
